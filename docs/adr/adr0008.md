# 📦 ADR-008: Separar ajuste de estoque do update de catálogo do produto

## ✅ Status

Aceito

## 🧩 Contexto

Durante o design do contrato OpenAPI do `product-service`, o `PUT /products/{id}` inicialmente incluía o campo
`inventory` (estoque) junto com os dados de catálogo (`name`, `description`, `price`).

Esse desenho gera um risco real de concorrência: `PUT` é semanticamente uma substituição completa do recurso. Estoque,
porém, não é um dado de catálogo — é um contador transacional que muda com alta frequência e por motivos completamente
diferentes (venda de um pedido, reposição), não por edição manual de cadastro.

Cenário de risco identificado:

1. Um admin abre a tela de edição do produto; a UI carrega `inventory = 50`.
2. Enquanto o formulário está aberto, pedidos são criados e o estoque real cai para 47.
3. O admin salva o formulário só para corrigir o `price`, mas o payload ainda envia `inventory: 50` (valor desatualizado
   que estava na tela).
4. O `PUT` sobrescreve o estoque real de 47 de volta para 50 — pedidos processados nesse intervalo "somem" do controle
   de estoque.

Esse problema também é relevante para o roadmap do projeto: quando o `order-service` publicar o evento `OrderCreated`
(Fase 3, RabbitMQ), o `product-service` precisará reagir baixando estoque de forma incremental — não substituindo o
produto inteiro.

## 🎯 Decisão

- `PUT /products/{id}` passa a tratar **apenas** dados de catálogo: `name`, `description`, `price`. O campo `inventory`
  foi removido do `ProductUpdateRequest`.
- Um novo endpoint dedicado foi criado para ajuste de estoque:
  ```
  PATCH /products/{id}/inventory
  ```
- O ajuste de estoque é feito por **delta** (incremento/decremento), não por valor absoluto:
  ```yaml
  InventoryAdjustmentRequest:
    type: object
    required:
      - delta
    properties:
      delta:
        type: integer
        format: int32
        description: Quantidade a somar (positivo) ou subtrair (negativo) do estoque atual
  ```
  Um valor absoluto reintroduziria o mesmo problema de "última escrita vence" que motivou essa separação.
- `inventory` continua presente no `ProductRequest` (criação), pois na criação não existe estado anterior a
  sobrescrever — é necessário definir um estoque inicial.

## ⚖️ Consequências

**✅ Positivas:**

- Elimina o risco de sobrescrita acidental de estoque por uma edição de catálogo concorrente.
- O endpoint de estoque já nasce no formato (delta) que o `order-service` vai precisar consumir na Fase 3, quando
  estoque for decrementado a partir do evento `OrderCreated`.
- Separação clara de responsabilidades: "editar produto" e "movimentar estoque" são operações de negócio distintas,
  agora refletidas no contrato.

**⚠️ Negativas / trade-offs:**

- Mais um endpoint para implementar e testar.
- Consumidores da API precisam saber que **não podem** ajustar estoque via `PUT /products/{id}` — precisa estar bem
  documentado no contrato/README do serviço.

## ❓ Pendente de decisão futura

Definir a regra de negócio para quando um `delta` deixaria o estoque negativo: bloquear com `400`, ou permitir
(representando "vendido sem estoque" para ajuste posterior)? Ainda não decidido — avaliar ao implementar a regra no
`service`.
