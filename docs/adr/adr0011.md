# 🚨 ADR-0011: Padronização de respostas de erro com ProblemDetail (RFC 7807)

## ✅ Status

Aceito

## 📅 Data

2026-08-29

## 🧩 Contexto

O contrato inicialmente usava um schema `Error` customizado (`code` + `message`), referenciado apenas nas respostas `default` de cada operação. Isso trazia duas lacunas:

1. As respostas `400` (requisição inválida) não tinham `content`/schema algum — só uma `description` solta, deixando o consumidor da API sem saber o formato real do corpo de erro numa falha de validação.
2. O schema `code`/`message` era suficiente para um erro genérico (ex.: "produto não encontrado"), mas não permitia expressar erro de validação **por campo** (ex.: qual campo falhou e por quê), algo necessário para o cliente exibir feedback específico ao usuário final.

O Spring Boot já oferece suporte nativo ao formato `ProblemDetail`, baseado na RFC 7807 (`application/problem+json`), via `ResponseEntity<ProblemDetail>` e extensão de propriedades customizadas (`setProperty(...)`). Adotar esse padrão evita reinventar serialização de erro e aproveita integração pronta do framework.

## 🎯 Decisão

- O schema `Error` foi substituído por `ProblemDetail`, com os campos padrão da RFC 7807 (`type`, `title`, `status`, `detail`, `instance`) mais uma extensão `errors` para detalhamento de validação por campo:
  ```yaml
  ProblemDetail:
    type: object
    properties:
      type:
        type: string
        format: uri
      title:
        type: string
      status:
        type: integer
        format: int32
      detail:
        type: string
      instance:
        type: string
        format: uri
      errors:
        type: array
        items:
          type: object
          properties:
            field:
              type: string
            message:
              type: string
  ```
- Todas as respostas `400`, `404` e `default` de todas as operações do contrato passam a referenciar `ProblemDetail`, com `content`/schema explícito — nenhuma resposta de erro fica mais sem corpo definido.

## ⚖️ Consequências

**✅ Positivas:**

- Aproveita suporte nativo do Spring Boot para `ProblemDetail`, sem precisar implementar serialização de erro customizada.
- Formato padronizado (RFC 7807) facilita consumo por clientes que já conhecem a convenção, incluindo o futuro client Angular.
- Extensão `errors` permite comunicar falhas de validação campo a campo, útil para formulários (ex.: Angular) exibirem mensagens específicas.
- Todas as respostas de erro do contrato agora têm schema explícito — elimina a lacuna anterior nos `400`.

**⚠️ Negativas / trade-offs:**

- `errors` é uma extensão não padronizada da RFC 7807 (o Spring permite, mas não é um campo "oficial" do `ProblemDetail`) — precisa ficar documentado no contrato para não gerar confusão com implementações que sigam a RFC à risca.
- Qualquer consumidor que já esperasse o formato antigo (`code`/`message`) precisaria se adaptar (não há consumidores reais ainda neste projeto de estudo).
