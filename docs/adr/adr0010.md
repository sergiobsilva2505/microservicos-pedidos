# 📄 ADR-0010: Paginação no findAll com envelope ProductPage

## ✅ Status

Aceito

## 🧩 Contexto

O `GET /products` (findAll) originalmente retornava um array puro com todos os produtos do catálogo. Esse formato
funciona bem com poucos registros, mas não escala: conforme o catálogo cresce, cada chamada carregaria a base inteira de
uma vez, sem controle de volume nem forma de o cliente pedir "a próxima página" de resultados.

Adicionar paginação implica duas mudanças de contrato, não apenas um detalhe de implementação:

1. Parâmetros de entrada para controlar o recorte de dados retornado.
2. Mudança do formato de saída: de um array puro para um objeto que carrega os itens **e** metadados sobre a paginação
   (página atual, tamanho, total de elementos, total de páginas) — sem os metadados, o cliente não sabe se existe mais
   conteúdo a buscar.

## 🎯 Decisão

- `GET /products` passa a aceitar os query params `page` (índice da página, `default: 0`) e `size` (itens por página,
  `default: 20`).
- A resposta `200` deixa de referenciar `ProductResponse` como array direto e passa a referenciar um novo schema,
  `ProductPage`:
  ```yaml
  ProductPage:
    type: object
    properties:
      content:
        type: array
        items:
          $ref: '#/components/schemas/ProductResponse'
      page:
        type: integer
        format: int32
      size:
        type: integer
        format: int32
      totalElements:
        type: integer
        format: int64
      totalPages:
        type: integer
        format: int32
  ```
- Os nomes dos campos (`content`, `page`, `size`, `totalElements`, `totalPages`) seguem deliberadamente a convenção do
  `Page<T>` do Spring Data, já que o serviço será implementado em Spring Boot — evita reinventar nomenclatura quando o
  próprio framework já expõe esse contrato via `Pageable`/`Page`.

## ⚖️ Consequências

**✅ Positivas:**

- Evita carregar o catálogo inteiro em uma única resposta conforme a base cresce.
- Cliente da API consegue navegar entre páginas e saber quando não há mais conteúdo (via `totalPages`).
- Nomenclatura alinhada ao Spring Data reduz fricção na hora de mapear o `Page<Product>` retornado pelo repository para
  o DTO de resposta.

**⚠️ Negativas / trade-offs:**

- Quebra de compatibilidade para qualquer consumidor que já esperasse um array puro em `GET /products` (não há
  consumidores reais ainda nesse projeto de estudo, mas fica registrado como padrão daqui pra frente).
- Mais um schema para manter sincronizado (`ProductPage`) além do `ProductResponse`.

## ❓ Pendente de decisão futura

Nenhuma pendência aberta neste momento — parâmetros de ordenação (`sort`) não foram incluídos nesta rodada e podem ser
avaliados como evolução futura, se necessário.
