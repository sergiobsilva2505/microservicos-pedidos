# 📄 ADR-00X: Uso de WebClient para comunicação síncrona entre order-service e product-service

**Status:** ✅ Aceita

**Data:** 2026-08-28

---

## 🧭 Contexto

O `order-service` precisa consultar o `product-service` de forma síncrona para obter os dados do produto no momento da
criação de um pedido (o dado é então persistido como snapshot dentro do próprio pedido). Essa comunicação ocorre via
REST, dentro da Fase 2 do projeto (comunicação síncrona).

O Spring oferece duas opções principais para chamadas HTTP entre serviços: `RestTemplate` e `WebClient`.

---

## ✅ Decisão

Será utilizado o **WebClient** (do módulo `spring-webflux`) para todas as chamadas HTTP síncronas do `order-service` em
direção ao `product-service`.

---

## ⚖️ Alternativas consideradas

### 🔴 RestTemplate

- É a opção mais tradicional e ainda amplamente usada em tutoriais e projetos legados.
- Está em **manutenção modo legado** desde o Spring 5 — não recebe novas funcionalidades.
- API baseada em bloqueio de thread (síncrona por natureza, sem suporte nativo a programação reativa).
- Foi descartado por não ser mais o caminho recomendado pela própria documentação oficial do Spring, mesmo em cenários
  onde o uso é síncrono.

### 🟢 WebClient

- Sucessor oficial do RestTemplate, parte do ecossistema reativo do Spring (WebFlux).
- Pode ser usado tanto de forma reativa (não-bloqueante) quanto de forma síncrona (via `.block()`), o que dá
  flexibilidade para o projeto evoluir sem trocar de ferramenta.
- É o caminho recomendado atualmente pela documentação do Spring para novos projetos.
- Prepara o terreno para uma eventual migração a chamadas assíncronas/reativas no futuro, caso o projeto evolua nessa
  direção.

---

## 📊 Consequências

### 👍 Positivas

- Código alinhado com as práticas atuais recomendadas pelo Spring.
- Flexibilidade para evoluir de chamadas bloqueantes para reativas sem reescrever a camada de integração.
- Menor risco de débito técnico por depender de uma API em manutenção legada.

### 👎 Negativas

- Curva de aprendizado um pouco maior que o RestTemplate, especialmente ao lidar com tipos reativos (`Mono`, `Flux`),
  mesmo quando usado de forma bloqueante.
- Uso de `.block()` para simular comportamento síncrono é considerado um "anti-padrão" no mundo reativo puro — aceitável
  aqui, mas deve ser revisado se o projeto migrar totalmente para reativo.
