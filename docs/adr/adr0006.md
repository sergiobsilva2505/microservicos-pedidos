# 📄 ADR-0006: Payload do evento OrderCreated — ID vs Dados completos

## ✅ Status

Aceito

## 📅 Data

2026-08-28

## 🧩 Contexto

Quando um pedido é criado, o `order-service` publica um evento `OrderCreated` no RabbitMQ, que será consumido pelo `notification-service` (e possivelmente outros consumidores no futuro). Era preciso decidir se esse evento carrega apenas o ID do pedido (exigindo que o consumidor busque os detalhes via chamada síncrona) ou o payload completo com todos os dados relevantes do pedido.

## 🎯 Decisão

O evento `OrderCreated` carregará o **payload completo** dos dados do pedido, não apenas o ID.

## 🔀 Alternativas consideradas

### 🔴 Apenas o ID do pedido
- Payload mais enxuto e evento mais simples de definir inicialmente.
- Obrigaria o `notification-service` (ou qualquer outro consumidor futuro) a fazer uma chamada síncrona de volta ao `order-service` para buscar os dados — o que reintroduz acoplamento síncrono dentro de um fluxo que deveria ser assíncrono, além de criar dependência de disponibilidade do `order-service` no momento do consumo do evento.
- Vai contra um dos principais benefícios de mensageria: desacoplamento entre produtor e consumidor.

### 🟢 Payload completo
- O consumidor recebe tudo que precisa diretamente no evento, sem depender de nenhuma chamada adicional.
- Mantém o desacoplamento real entre `order-service` e `notification-service`: o consumidor pode processar o evento mesmo que o `order-service` esteja fora do ar naquele momento.
- Alinhado ao padrão *event-carried state transfer*, comum em arquiteturas orientadas a eventos no mercado.

## ⚖️ Consequências

**✅ Positivas:**
- Desacoplamento real entre produtor e consumidor do evento.
- Consumidores futuros (além do `notification-service`) podem reagir ao evento sem chamadas adicionais.
- Resiliência maior: falha ou indisponibilidade do `order-service` não impede o processamento do evento já publicado.

**⚠️ Negativas / trade-offs:**
- Payload maior trafegando pela fila, comparado a um evento minimalista com apenas o ID.
- Qualquer mudança na estrutura do pedido exige atenção ao contrato do evento (versionamento do evento se torna uma preocupação relevante no futuro).
